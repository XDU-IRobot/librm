# 简介

librm 是西安电子科技大学 IRobot 战队开发的 Robomaster 嵌入式电控框架，提供 STM32 和 Linux 上的外设封装、设备驱动与控制算法。它把通信、协议解析和常用控制模块整理在一起，方便开发者把时间花在机器人的控制逻辑上。说得直接一点，就是省事好用。

一台性能优异的机器人离不开大量花在尝试控制方案、调试算法、优化参数上的时间，但在此之前，开发者往往要花费大量时间在与控制逻辑无关的工作上：查手册、配外设、处理协议、移植驱动、写离线检测、等等。

librm 把这些反复用到的底层工作封装成完善且标准化的模块，减少不同机器人、不同项目之间的重复开发，让开发者有更多时间来做有意义的事情。

本项目由西安电子科技大学 IRobot 战队在 2024 赛季启动开发，以 MIT 协议开源。欢迎各参赛队和机器人开发者使用，如果觉得好用的话，star plz！如果有任何问题或建议，欢迎提 issue/pr!

## 从这里开始

librm 通过 CMake 接入已有工程：

```cmake
add_subdirectory(librm)
target_link_libraries(${PROJECT_NAME} PRIVATE rm)
```

首次使用请先按平台完成配置：[STM32 / CubeMX](../integration/stm32_cubemx.mdx) 或 [Linux / CMake](../integration/linux_cmake.mdx)。之后可以从[电机驱动教程](../tutorials/motor-drivers.mdx)开始，也可以先查看[完整功能与支持状态](./features.mdx)，确认需要的设备和模块是否已有实现。

## 你可以用 librm 做什么

### 把外设初始化那些坑替你踩完

以 CAN 为例。STM32 HAL 的 `CAN_InitTypeDef` 有十来个字段，位时序、SJW、FIFO 锁定、自动重传各有各的语义；过滤器要按寄存器格式算 ID 和 mask；收发的 mailbox 数量、BUS-OFF 恢复、回调注册又各有讲究。这些配置单看文档都能配，但配错一项的现象往往只是"不通信"或"偶尔丢帧"，排查一次就够喝一壶。

而机器人上一条 CAN 总线，绝大多数时候的需求就是一个波特率加上收发。librm 按这个假设封装了一层：

```cpp
rm::hal::Can can(&hcan1);
can.Begin();                                    // 注册回调、启动外设、使能中断

rm::hal::CanFrame frame{};
frame.std_id = 0x200;
frame.dlc = rm::hal::CanFrame::kDlc8;
can.Write(frame);                               // 等待 mailbox / 处理 BUS-OFF 交给封装
```

CubeMX 里选好外设和波特率，剩下的调用顺序和 corner case 由 librm 处理。需要更细的控制时，HAL 句柄还在你手里。

串口、GPIO、定时器同样遵循上述思想，提供相应的简易HAL封装。

接进已有工程只需要在 CMakeLists 里加两行：

```cmake
add_subdirectory(librm)
target_link_libraries(${PROJECT_NAME} PRIVATE rm)
```

不需要额外的构建系统，没有各种闹不清的配套工具。

### 模块组合能力

librm 的模块共享统一的类型定义、CAN 抽象和错误处理方式，可以在业务代码中直接连接，减少重复适配。下面的片段大致展示了使用 librm 进行开发时数据如何流转。

```cpp
// 组合示例：限功率底盘控制。将裁判系统、功率模型、PID、底盘运动学、CAN限流组合在一起
rm::hal::ThrottledCan<128> can(1000, &hcan1);       // 定频 1kHz 发送，防止总线拥塞
rm::device::Referee<rm::device::RefereeRevision::kV170> ref;
rm::modules::MotorPowerModel power_model(rm::modules::MotorPowerModel::kM3508);
rm::modules::MecanumChassis chassis(0.3f, 0.4f);

const auto power_limit = ref.data().robot_status.chassis_power_limit;  // 裁判系统 -> 功率上限
const auto [v_lf, v_rf, v_lr, v_rr] = chassis.Forward(vx, vy, w);              // 运动学 -> 四轮目标转速
power_model.DistributePower<4>(states, currents, power_limit, output); // 功率模型 -> 限幅
```

### 跨平台能力

STM32 和 Linux 使用相同的外设接口，但创建外设对象时需要传入各自的平台参数。例如，STM32 的 CAN 使用 HAL 句柄，Linux 使用 SocketCAN 接口名。完成这一步后，上层的设备驱动和控制算法都可以复用。

```cpp
// Linux: rm::hal::Can can{"can0"};
/*STM32:*/ rm::hal::Can can(&hcan1);
rm::device::M3508 motor(can, 1);                    // M3508 电机，ID=1
rm::modules::PID pid(10, 0.5, 0, 16384, 5000);      // 速度环 PID

can.Begin();
while (true) {
    pid.Update(target_rpm, motor.rpm());            // 速度闭环
    motor.SetCurrent(pid.out());                    // 电流输出
    rm::device::DjiMotorBase::SendCommand();        // 发送 CAN 帧
    rm::core::SleepMs(1);
}
```

这便于在 Linux 上调试设备驱动、测试算法，再接入 STM32 工程。同时，还有更多可以简化工作流的用法，比如：

- Linux上位机和STM32下位机用 `rm::device::CanDevice` 类进行相互通信，代码清晰可读：

  ```cpp
  /// STM32眼里的Jetson上位机，放在STM32端的代码
  class Jetson : public rm::device::CanDevice {
  public:
    explicit Jetson(rm::hal::CanInterface &can, uint16_t host_frame_id = 0x200)
        : CanDevice{can}, host_frame_id_(host_frame_id) {}

    // 发送关节状态给上位机
    void FeedbackJs(const JointState &js) const {
      rm::hal::CanFrame tx{.std_id = 0x100, .dlc = rm::hal::CanFrame::kDlc64, .is_fd_frame = true};
      std::memcpy(tx.data.data(), &js, sizeof(js));
      can_->Write(tx);
    }

  private:
    void RxCallback(const rm::hal::CanFrame *msg) override {
      if (msg->std_id != host_frame_id_) return;
      // ...
      // 上报设备状态给rm::device::Device基类，由rm::device::DeviceManager处理设备的在线监测和离线保护
      ReportStatus(kOk);  // Jetson在线！
    }

    uint16_t host_frame_id_;
  };

  /// Jetson上位机眼里的STM32，放在STM32端的代码
  class STM32 : public rm::device::CanDevice {
  // ...
  private:
    void RxCallback(const rm::hal::CanFrame *msg) override {
      // 处理收到的JointState...
      ReportStatus(kOk);  // STM32在线！
    }
  };
  ```

- 裁判系统串口的TX线并联到Linux上位机上，上位机可以用 `rm::device::Referee` 类直接拿到裁判系统数据，不需要电控转发。
- 无下位机控制。（虽然我强烈不推荐使用这种方案，控制效果和稳定性极差！）

:::warning
实际应用中，由于Linux和STM32这种MCU平台存在实时性以及并行行为上的差异，仍然需要考虑线程、中断环境以及控制周期抖动问题。
:::
